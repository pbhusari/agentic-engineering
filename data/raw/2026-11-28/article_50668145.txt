Credit card skimming scripts using WebRTC found on popular shopping sites — InfoHawk News Info Hawk Product News Team Contact us ← All news November 27, 2026 Credit card skimming scripts using WebRTC found on popular shopping sites All the sites we contacted took action; but the larger consumer web ecosystem should be prepared to mitigate these attack vectors A card-skimming script was planted on the online stores of Lascana, Samsonite, American Tourister, Revolve and FWRD in the week before Black Friday. After our reports to affected companies, all have had the script removed (on November 24th or 25th) ahead of Black Friday. We observed it in action on one of the five websites: Lascana, where it sent our test card's details to a 3rd party. We believe the script was built to take a card number, expiry and security code, along with a user's name, address, phone and email, and send them to malefactors as a user entered their payment credentials. It did this before the store checked the payment, so a card could be taken even if the order was declined or cancelled, and nothing would look wrong to the shopper. Across all of these sites, we do not know how many, if any, shopper details or payment credentials may have been captured. How the attack works This attack uses WebRTC, the technology that allows you to make video calls in your web browser. WebRTC lets a web page open its own channel to another party and pass data (e.g. audio/video packets) over it. It has likely been used (both to load the skimmer and to send the stolen card details out) because security rules and monitoring tools often do not watch this communications channel as closely. For example, Meta briefly used WebRTC in a creative way in 2025 , according to researchers looking at the technology as a compromise vector. This form of attack appears to target mobile devices, and we only saw the server enable the skimmer on checkout pages, so desktop checks and homepage scans would likely not see it. The skimmer's traffic appeared to run through Cloudflare's relay, so it would blend in with the WebRTC traffic and hide its true endpoint. Worried that your card was compromised? Check your recent statements for charges you don't recognize, especially on debit cards. Call your bank or card issuer right away, report the fraud and ask for a new card number. Follow up with a written dispute within 60 days of the statement that shows the charge. Our understanding of US federal law is that your liability for unauthorized credit card charges is capped at $50, and is generally zero if only your card number was stolen, as in a skimming attack like this one. Debit cards have weaker protections that depend on how quickly you report, so act fast. For more information, see “ Additional resources ” below. What site owners should immediately do On every page that takes payment, set a connect-src rule that lists only the hosts you use. That blocks the two web requests the script needs before WebRTC opens. Without them the skimmer never arrives, whichever file was tampered with. What security teams should look for We saw the skimmer delivered in three different ways across five websites run by different companies, and all of them appear to rely on the same attacker infrastructure. That makes it likely that other sites are affected too, so we encourage online retailers to check their own sites for the signs below. Script sources: search page source, tag managers, consent-banner settings and CDN files for scripts from &lt;brand&gt;-static.s3.amazonaws[.]com (files Insds.js , gtage.js ). We believe this is the malicious code. Tracking pixels: if you load qscripts.s3.amazonaws[.]com/pscript.js , check its last line for one of the above CDN buckets, and if present, remove the tracking pixel. We recommend reviewing all similar tracking pixels and their exposure to sensitive fields or actions on your website. Seers banners: If you have integrated Seers, open your banner config ( cdn.seersco.com/banners/&lt;account&gt;/&lt;domain&gt;/cb.js ) and check that every URL field holds only a URL. In the affected configs, the privacy-policy link field also held a hidden image, whose onerror event handler loaded the malicious code. Checkout traffic: on a phone-sized touch screen, at the payment step, look for /_cf/ice and /_cf/rel requests to *.northbridgeads[.]com and a relay-only WebRTC connection used by the malicious code. Desktop checks miss it. Strings: KghRtc , rtc-signal-v1 and quickfetch are referenced in the malicious code and may warrant further investigation if present. The industry is not ready for the scale of supply chain attacks coming This attack takes advantage of a few critical design decisions in websites that, if improperly configured, allow malicious actors to broadly deploy and trigger exploits across the open web. Websites load third-party code, often through a tag manager, from servers they don't control. The vendor can change that code at any time, and it can pull in further third-party code the site never reviewed. That code runs as an ordinary script with the same rights as the site's own code. It can read and rewrite the page, watch what users type, and load more code. Login, personal-information and payment pages often load the same marketing scripts as the rest of the site. Card fields should sit in an isolated payment frame, and third-party tags should be kept off these pages entirely. Loading third-party tracking pixels on checkout, payment and login pages is far too common a practice today. Each pixel can run whatever code its vendor's file holds, including a skimmer, and whoever controls that file can change it without the site noticing. Every site should review which tracking pixels load on pages that take payment or sign-in details, who can change those files, and whether they need to be there at all. A similar weakness was exploited at scale on 16 November 2026. An attacker reportedly used a flaw in Optimizely's Web Experimentation product to add malicious code to customers' projects, and Optimizely's own servers delivered it to visitors of 178 organizations' sites, including Zoom, the BBC and CNN, with no change to those sites' own code.
