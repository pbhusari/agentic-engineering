eMudhra Intermediate CA Compromise eMudhra Intermediate CA Compromise 20th October 2026 The private keys of eight eMudhra intermediate CA certificates have been compromised. They chain to roots trusted by the Mozilla, Microsoft, Apple and Chrome root programs and by many downstream trust stores. How do we know? To demonstrate that the keys are compromised, the original reporter Wayne signed the following message with the private key of each of the eight intermediate CAs and reported it to the Root Program Teams on the 17th of October: We have a problem here - Wayne proof.zip contains the message, and for each intermediate the certificate, its public key and a signature on the message. To verify with OpenSSL: openssl x509 -in EM-DV-TLS-CA-G3B.crt.pem -noout -pubkey | diff - EM-DV-TLS-CA-G3B.pub.pem openssl dgst -sha384 -verify EM-DV-TLS-CA-G3B.pub.pem -signature EM-DV-TLS-CA-G3B.sig message.txt What actions have been taken? The root programs and many downstream trust stores have taken action to protect their users. The certificates have been blocked in Firefox and Chrome since the 17th of October, in Apple devices since the 19th and on Microsoft platforms since the 20th. The issue was responsibly disclosed to downstream trust stores on the 19th of October. Many have already released updates or are in the process of releasing updates. What are the consequences? An attacker with the private key of any of the compromised intermediate CAs could impersonate any website or service. This has already been remediated by Mozilla, Microsoft, Apple, and Chrome for their users through their tools for distributing revocation information such as OneCRL , CRLite and CRLSets . The CA has also revoked the compromised intermediate certificates. However, many other clients do not consume revocation information and require software updates to ensure they no longer trust the compromised intermediates. Which intermediates were compromised? impacted-intermediates.json lists the eight intermediates and their Sectigo cross-signs. roots.json lists the roots they chain to. What is known about the cause? The private keys for the intermediate certificates were incorrectly generated by the CA. This means that anyone can recover them from the certificates. This would have been possible since the certificates were created in April 2025. There are no entries in the certificate transparency logs for these intermediates in that period, indicating that CT-enforcing clients like Firefox, Chrome, Edge and Safari could not have been attacked. However, many clients outside of the browser ecosystem do not enforce Certificate Transparency. We do not know if attackers exploited the flawed key generation to target these clients. Further technical information about the cause is captured in the initial incident report in Mozilla's bug tracker. What actions can trust store operators take? Please see this thread in Mozilla's dev-security-policy forum. What actions can users take? Users should update their browsers and operating systems to the latest versions as soon as possible. Are there workarounds for macOS curl, git, and Python? macOS blocks the compromised intermediates, but the built-in curl , git , python3 , perl , ruby , and openssl verify certificates against /etc/ssl/cert.pem without checking revocation, and that file has not been updated. To remove the affected roots from it, run: sudo cp -p /etc/ssl/cert.pem /etc/ssl/cert.pem.bak &amp;&amp; sudo awk '/^(###|===) /{skip=0} /^=== .*\/CN=(AAA Certificate Services|emSign ECC Root CA - G3)$/{skip=1} !skip' /etc/ssl/cert.pem.bak | sudo tee /etc/ssl/cert.pem &gt; /dev/null The built-in pip3 , and the pip in virtual environments created from the built-in python3 , use their own outdated copy of the roots instead. To make them use the fixed system file, run: F="$(/usr/bin/python3 -c 'import sysconfig; print(sysconfig.get_path("stdlib"))')/sitecustomize.py" &amp;&amp; echo 'import os; os.environ.setdefault("PIP_CERT", "/etc/ssl/cert.pem")' | sudo tee -a "$F" &gt; /dev/null &amp;&amp; sudo chmod 644 "$F" Are there workarounds for Linux? Until a distribution ships an updated ca-certificates package, expert users can distrust the affected roots in the system trust store. This is NOT recommended for ordinary users. On Debian and Ubuntu, run as root: sed -i \ -e 's|^mozilla/emSign_ECC_Root_CA_-_G3.crt|!&amp;|' \ -e 's|^mozilla/Comodo_AAA_Services_root.crt|!&amp;|' \ /etc/ca-certificates.conf &amp;&amp; update-ca-certificates On Alpine, run as root: apk add ca-certificates &amp;&amp; sed -i -e 's|^mozilla/emSign_ECC_Root_CA_-_G3.crt|!&amp;|' \ /etc/ca-certificates.conf &amp;&amp; update-ca-certificates On Fedora, RHEL, CentOS Stream, Rocky Linux, AlmaLinux and Amazon Linux 2023, run as root: d=/etc/pki/ca-trust/source/blocklist; [ -d $d ] || d=/etc/pki/ca-trust/source/blacklist trust extract --overwrite --format=pem-bundle \ --filter='pkcs11:object=Comodo%20AAA%20Services%20root;type=cert' \ $d/Comodo_AAA_Services_root.pem &amp;&amp; trust extract --overwrite --format=pem-bundle \ --filter='pkcs11:object=emSign%20ECC%20Root%20CA%20-%20G3;type=cert' \ $d/emSign_ECC_Root_CA_-_G3.pem &amp;&amp; update-ca-trust On openSUSE and SLES, run as root: d=/etc/pki/trust/blocklist; [ -d $d ] || d=/etc/pki/trust/blacklist trust extract --format=pem-bundle \ --filter='pkcs11:object=Comodo%20AAA%20Services%20root;type=cert' \ $d/Comodo_AAA_Services_root.pem &amp;&amp; trust extract --format=pem-bundle \ --filter='pkcs11:object=emSign%20ECC%20Root%20CA%20-%20G3;type=cert' \ $d/emSign_ECC_Root_CA_-_G3.pem &amp;&amp; update-ca-certificates On Arch Linux, run as root: trust extract --format=pem-bundle \ --filter='pkcs11:object=emSign%20ECC%20Root%20CA%20-%20G3;type=cert' \ /etc/ca-certificates/trust-source/blocklist/emSign_ECC_Root_CA_-_G3.pem &amp;&amp; update-ca-trust On NixOS, add to your configuration: security.pki.caCertificateBlacklist = [ "Comodo AAA Services root" "emSign ECC Root CA - G3" ]; Are there workarounds for NetBSD? On NetBSD 10 and later, run as root: certctl untrust /usr/share/certs/mozilla/all/emSign_ECC_Root_CA_-_G3.pem &amp;&amp; certctl untrust /usr/share/certs/mozilla/all/Comodo_AAA_Services_root.pem Are there workarounds for FreeBSD?
