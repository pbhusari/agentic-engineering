For the past few years, all of the major browser vendors (Google, Apple, Microsoft, and Mozilla, along with Igalia and Bocoup) have been working together on Interop (opens in new tab) , a project to improve universal browser support on web technologies. It’s been a remarkably successful effort; when a focus area gets added to Interop, it often winds up reaching near-100% support across all major browsers within a year. ✨ CSS Subgrid is a good example. Subgrid is a super-powerful extension to CSS Grid which enables entirely new layouts . It was implemented in Firefox back in 2019, but there wasn’t much movement with other browsers for years. It got added to Interop 2023, and by the end of that year, it was widely available across all modern browsers: The Y axis shows the percentage of tests related to subgrid passing in each browser. The black “Interop” line shows tests passing in all browsers. As we reach the end of 2026, Interop 2027 is currently being planned, and the team at Mozilla has created a ranking system (opens in new tab) for us to upvote our most-requested features. They plan on using the ranking data to decide what to include for next year’s Interop! In this blog post, I want to dig into the top 10 features I voted for, to offer a bit of a preview of what CSS might look like within the next year. There will also be some little tips and tricks you can start using today! Link to this heading 1. CSS functions Current Browser Support Supported in Chrome 155 and Edge 154 Not supported in Firefox 157 Not supported in Safari 27 Current as of October 2026 . More info on caniuse (opens in new tab) One of the most exciting ideas is the proposal to add functions to CSS (opens in new tab) : Copy to clipboard /* Define a function: */ @ function --gradient-to-transparent(--color, --direction: bottom) { result: linear-gradient( to var(--direction), var(--color), transparent; ); } /* Invoke it: */ . elem { background : --gradient-to-transparent( red ) ; } /* …which produces: */ . elem { background : linear-gradient ( to bottom , red , transparent ; ); } If you’re familiar with JavaScript, this should feel pretty familiar. We define new functions with @function and specify the returned value with result . There’s so much cool stuff we can do with this. Personally, the use case I’m most interested in is the ability to convert between polar and cartesian coordinates, a concept we use over and over in my Whimsical Animations course (opens in new tab) : Copy to clipboard @ function --translate-polar(--angle, --distance) { result: translate( calc(cos(var(--angle)) * var(--distance)), calc(sin(var(--angle)) * var(--distance)) ); } /* Move this element 100px at a 45° angle: */ . particle { transform : --translate-polar( 45 deg , 100 px ) ; } This feels pretty “science-fiction” to me, but it’s already implemented in Chromium browsers, and if it gets added to Interop 2027, I think there’s very good odds that it could become widely available sooner rather than later! Anchored Container Queries Current Browser Support Supported in Chrome 155 and Edge 154 Not supported in Firefox 157 Not supported in Safari 27 Current as of October 2026 . More info on caniuse (opens in new tab) I recently published a blog post on Anchor Positioning , one of the most exciting modern CSS features (which was actually prioritized in Interop 2026, and is now widely available!). The Anchor Positioning API allows us to anchor one element to another. For example, we might anchor a floating tooltip element to its trigger, so that no matter where that trigger is on the page, the tooltip will always be connected to it. If you’ve ever tried to solve this sort of problem yourself, you know it’s surprisingly tricky. For example, we might want our tooltip to float above the anchor, but what if the anchor is near the top of the viewport? This is a tooltip displaying additional information about this button. Example button The tooltip fits comfortably. This is a tooltip displaying additional information about this button. Example button The tooltip’s getting cut off! The original Anchor Positioning API gave us most of the tools needed to solve this problem easily in CSS. It allows us to specify fallback positions; if the target element doesn’t fit above the anchor, it can flip automatically to the bottom. The only thing missing was the ability to tell whether or not the target had flipped. We had no way to know, in CSS, whether the target element is currently sitting above or below the anchor, whether it’s using the default or fallback position. For tooltips, this is a problem because we typically want to add a little protrusion that points towards the anchor. The “Level 2” version of the Anchor Positioning API includes a new type of container query that allows us to check whether the target element is using a fallback position or not. You can learn more about it in my Anchor Positioning blog post , or check out the Interop 2027 proposal (opens in new tab) . Link to this heading 5. Scroll-triggered animations Current Browser Support Supported in Chrome 155 and Edge 154 Not supported in Firefox 157 Not supported in Safari 27 Current as of October 2026 . More info on caniuse (opens in new tab) In my blog post on scroll-driven animations , we explore how we can scrub through a keyframe animation by scrolling. For example, we can use it to fade an element in as it traverses the viewport: 100 % 80 % 60 % 40 % 20 % 0 % Scroll-driven animations were part of Interop 2026 (opens in new tab) , and it’s been successfully implemented across all browsers. In addition to Scroll- driven animations, however, there’s a separate proposal for scroll- triggered animations . With scroll-triggered animations, the goal is to trigger a keyframe animation when the user scrolls to a specific point, like a proximity sensor going off. At that point, the animation runs normally over a specified duration. We can currently implement scroll-triggered animations using the IntersectionObserver API in JavaScript, but it’s kind of a pain. It’ll be super nice when we can use CSS for both scroll-driven and scroll-triggered animations, since they each have their own use cases. CSS reading-flow and reading-order Current Browser Support Supported in Chrome 155 and Edge 154 Not supported in Firefox 157 Not supported in Safari 27 Current as of October 2026 . More info on caniuse (opens in new tab) I’m currently working on a top-secret project which involves a dynamic grid-based layout. Items are arranged very differently on desktop vs. mobile: Desktop Layout Mobile Layout This is one of the great things about responsive CSS, but it leads to an unfortunate side effect: tab order is always based on the DOM order, not the visual order. So, if someone uses assistive technologies to navigate between elements, that navigation order will always be the same, even as the layout changes dramatically depending on screen size. On desktop, the first visual item is that list of Redacted sounds on the left, but on mobile, the first item is that big red button. Whichever element comes first in the DOM will be the first item to receive focus, which will invariably be wrong for a percentage of our users. Thankfully, the new reading-flow property grants us a solution to this problem, and there’s a proposal for Interop 2027 (opens in new tab) . The basic idea is that we can specify that the tab order should follow one of several visual orders: Copy to clipboard . grid { display : grid ; reading-flow : grid-rows ; } There are values for both CSS Grid and Flexbox, and if you need even more control, the reading-order property allows us to create a custom order, sorta like tabIndex in HTML. This property has been championed by one of my personal heroes, Rachel Andrew. You can read more about it in her blog post on reading-flow . Link to this heading 8. CSS gap decorations Current Browser Support Supported in Chrome 155 and Edge 154 Not supported in Firefox 157 Not supported in Safari 27 Current as of October 2026 . More info on caniuse (opens in new tab) One of the things that makes CSS Grid layout unique is that the grid children are positioned using rows/columns defined entirely in CSS. In every other layout mode, elements are positioned using other elements! In Table layout, for example, every grid cell has an associated &lt;td&gt; or &lt;th&gt; element. There are a lot of upsides to CSS Grid, but one of the downsides is that it’s not as easy to add borders between grid cells. If a grid cell is empty, there’s no element to slap a border: 1px solid on! The gap decorations proposal (opens in new tab) introduces a new set of CSS properties that will allow us to use a border-like syntax on the grid itself.
