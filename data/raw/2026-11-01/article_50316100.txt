Jepsen: ParticleDB 1.1.4 JEPSEN Blog Analyses Talks Consistency Services Ethics ParticleDB 1.1.4 Kyle Kingsbury 2026-10-31 ParticleDB is a multi-model database designed for AI workloads. We tested versions 1.1.4 through 1.1.18.11.rc-22 and found that ParticleDB’s claims of “Full ACID” were somewhat premature. We present 96 issues in ParticleDB, ranging from the pedestrian (crashes, deadlocks, data loss, etc.) to the piquant (partially-invisible rows which could not be deleted, WHERE 4 = 5 , dropped tables re-emerging in distorted forms, confused columns, strings turning into integers, and so on). Most issues required just a single server, single client, and no faults. By version 1.1.18.11.rc-22, all but ten of those issues appeared resolved. However, ParticleDB continued to lose committed writes during normal operation with the default occ transaction mode, and allowed internal anomalies and Lost Update with serializable , the strongest setting. Orkes, the makers of ParticleDB, have since released version 1.1.19-rc.13; they claim that it resolves all remaining issues discussed in this report. This research was funded by Orkes, Inc., and conducted in accordance with the Jepsen ethics policy . 1 Background Modern applications often spread state across a variety of systems: databases, caches, queues, data warehouses, search indices, and so on. Coordinating these systems is challenging: caches are often stale, the analytics platform might lag days behind the primary database, the search index might lose data, and transactional updates across disparate systems remains an open research problem . ParticleDB 1 aims to unify these workloads in a single engine with a special focus on AI agents and applications. It offers transactional SQL, a key-value store, vector search, live analytics, and user-defined functions called Particles . 2 To integrate with existing systems, clients can connect through a variety of interfaces , including the Postgres and Redis protocols, as well as its own gRPC and HTTP2 APIs. Written from the ground up in Rust, ParticleDB claims to be orders of magnitude faster than Postgres while preserving the same safety characteristics. ParticleDB was built by Orkes to support their workflow orchestration platform, Conductor . Conductor was initially built to store data in Redis and Postgres, but to improve performance, Orkes opted to write their own database. ParticleDB 1.0.0 offered a limited feature set specifically for Conductor’s queries, and was deployed as the backing database for some of their Conductor clusters. A few Orkes customers followed suit. In preparation for a broader release, Orkes undertook a major refactoring of ParticleDB, adding a custom wire protocol, more datatypes, additional OLAP queries, and more. While Orkes and their customers continued to run 1.0.0, they soft launched the refactored versions on particledb.ai . Orkes engaged Jepsen to test these versions of ParticleDB, beginning with 1.1.4. While ParticleDB could run as a single node, it also offered a replicated cluster using the Raft consensus protocol. This replication feature was available only in enterprise cloud deployments. The builds Orkes provided did not support replication, so this report covers only single-node behavior. 1.1 Safety ParticleDB’s home page advertised that ParticleDB was “formally proven” with a TLA+ proof. However, during our collaboration no TLA+ specification was available. It is unclear what properties might be proven, or whether they described ParticleDB as built. ParticleDB offered three tactics for syncing its Write-Ahead Log (WAL). The sync mode called fsync on each commit, groupsync batched multiple transactions into a single fsync , and nosync skipped fsync altogether. The Transaction Engine documentation described sync as offering “stronger durability” than groupsync . On the other hand, particledb start --help said the groupsync mode ensured that “COMMIT waits for flush”, and Orkes’ internal operator guide concurred: groupsync offered the “same durability as sync ”. ParticleDB’s home page proudly claimed “Full ACID. 159K TPS.” However, the text immediately below this said “snapshot isolation”, which is not fully isolated . Most SQL databases use the SET TRANSACTION ISOLATION LEVEL statement to control the concurrent semantics of a transaction. However, ParticleDB ignored or rejected these statements . In some cases it instructed users to choose READ COMMITTED , a relatively weak isolation level. In other cases it accepted requests for different isolation levels, and silently ignored them (despite documentation to the contrary). Instead, transaction isolation was governed by the --txn-mode setting passed at startup. The transaction engine documentation described four modes : Mode Behavior When to use fast No locks; commit-on-write Bulk loads, single-writer benchmarks occ Overlay + commit-time OCC validation (default) General OLTP — safe under concurrency zero-copy-occ Partition-pinned OCC; single-partition txns skip cross-partition coordination High-throughput OLTP on partition-affine workloads (TPC-C, key-value) table-2pl Exclusive table locks at first touch Strictest serialization, simple semantics This table was difficult to interpret. While the best practices documentation warned that users should “pick --txn-mode deliberately”, since “it changes correctness and throughput characteristics more than SQL text does”, the documentation did not explain what these modes actually guaranteed. The fast mode was clearly intended for weaker isolation, but was that Read Atomic, Read Uncommitted, or something else? The occ mode was similarly unclear. “Commit-time OCC validation” could describe a broad spectrum of consistency models from Read Uncommitted to Strong Serializable, but “safe under concurrency” suggests it might be Serializable. The zero-copy-occ mode described a performance optimization which could be as safe as occ , but it was not described as “safe under concurrency”—raising the question: in what ways was it unsafe? Finally, if table-2pl offered the “strictest serialization”, was occ some weaker isolation level? The CLI reference page contained another table which described occ and table-2pl as “Jepsen-safe”, whereas fast was not “Jepsen-safe”, but did not explain their safety properties. Since Jepsen evaluates safety with respect to documentation and marketing claims, it is not clear how to interpret these terms. 3 Running particledb start --help provided the following table: Mode Description fast No locks, maximum OLTP throughput (unsafe under concurrency) occ Table locks + commit-time validation (safe for most OLTP) row-2pl Alias for occ zero-copy-occ Partition-pinned OCC (highest throughput safe mode) table-2pl Exclusive table locks, full serialization (strictest) serializable Alias for table-2pl serializable-ssi Adaptive SSI (Cahill 2008), PL-3 with optimistic semantics (v1 scaffolding — see SSI_ADAPTIVE_DESIGN.md) The point of Optimistic Concurrency Control (OCC) is generally to avoid taking locks, so the mention of table locks and a row-2pl 4 alias was surprising. Moreover, “safe for most OLTP” undermines the claim that occ was “safe under concurrency”; it suggests there are some OLTP workloads which are unsafe! Orkes explained that this documentation was wrong: occ was actually optimistic, and the row-2pl alias was to preserve compatibility with an earlier two-phase locking mechanism. They also provided an unpublished operator guide with detailed descriptions of the various transaction modes. This document was difficult to interpret , but did specify the following consistency models: Mode Consistency Model fast Unknown occ-v3 (a.k.a. occ , occ-v2 , row-2pl ) Snapshot Isolation zero-copy-occ (a.k.a. zocc ) Snapshot Isolation serializable-ssi (a.k.a. ssi ) Serializable table-2pl (a.k.a. serializable ) Strong Serializable Sources disagreed about the default transaction and WAL sync modes, but in general, occ-v3 and groupsync appeared to be the default. 2 Test Design We wrote a test suite for ParticleDB using the Jepsen testing library . We ran ParticleDB versions 1.1.4 through 1.1.18.11.rc-22 on individual Debian 13 nodes, both in containers and EC2 VMs. Our test harness could simulate process crashes by killing ParticleDB, simulate the loss of un- fsync ed writes using LazyFS , and truncate or corrupt disk files. We ran ParticleDB using each transaction mode and all three WAL sync modes. We first tried ParticleDB’s official Java SDK. While the documentation indicated that the library was available as a Maven dependency, neither the JAR nor source code were actually available. Instead, we began with the official Postgres JDBC client, version 42.7.11, and later added support for the ParticleDB Java SDK , versions 1.0.0 through 1.0.2. 2.1 Workloads We used several Jepsen workloads from other SQL databases, and designed new ones specifically for ParticleDB. The rw workload performed randomly generated transactions involving reads and writes of integer values identified by unique integer keys. We stored each value in a single row and accessed them both via primary and unindexed secondary keys. Keys and values were encoded as a variety of datatypes, including integers, decimals, and strings. We assumed that writes followed reads within each transaction, and that individual keys were sequentially consistent, and used these assumptions to infer constraints on the version orders and transaction dependency graphs . Jepsen’s transactional checker, Elle , then searched for cycles in that dependency graph, as well as a variety of non-cyclic phenomena like G1a (Aborted Read) . The append workload also performed randomly generated transactions over rows identified by unique integer keys, but the values were lists of integers. Transactions could read one of these lists by key, or append a unique integer to a list by key. We encoded each list as a comma-separated text field, and used SQL concat to append to them. Rows could be selected via primary key or unindexed secondary key, or via a join to an indirection table. From there, we used Elle to infer version orders and dependency graphs, and searched for a variety of cyclic and non-cyclic phenomena. When these workloads revealed consistency violations within a single transaction, we designed an internal workload to stress internal consistency. This workload performed a series of randomly generated transactions involving INSERT , UPDATE , DELETE , and SELECT statements over a simple key-value table, and verified that within each individual transaction, reads observed prior writes. To investigate tantalizing anomalies in the internal workload, we designed the compare workload. This workload used Clojure’s test.check generative testing library to produce random tables and simple SQL statements over them, then executed those statements against both ParticleDB and PostgreSQL. If ParticleDB’s behavior was not equivalent to PostgreSQL’s, the compare workload would search for a simpler sequence of statements that could reproduce the same divergence. Although our SQL generator was relatively simple—just a few basic datatypes, literals, arithmetic, comparisons, boolean logic, transactions, and some simple LIMIT , OFFSET , and ORDER BY clauses—it proved remarkably fruitful. Drawing on these successes, we devised a hybrid internal-sim workload to search for violations of internal consistency in more complex transactions. This workload generated a random set of tables, then concurrently executed random transactions over them. It then checked each transaction independently to ensure that each of its statements observed results consistent with those preceding. For example, if a transaction executed DELETE ... WHERE 2 &lt; c , then observed a row with c = 3 , we could prove that transaction was not internally consistent. 3 Results We found 96 issues with ParticleDB, which we present in several categories below. While some transactions might complete in a few milliseconds, most took 10, 20, or even 30 seconds, then failed. For example, take this test run with a single node running 1.1.18.4, transaction mode table-2pl , and WAL mode groupsync . With ten concurrent clients, most transactions blocked for tens of seconds before throwing could not serialize access due to concurrent update , or an IO error. High latencies ( #62 ) appeared improved by 1.1.18.6, which could execute transactions with sub-100 millisecond latencies for at least a few seconds. 3.1.2 Mystery Crash (#81) While 1.1.18.6 improved latencies, it also crashed frequently. Crashes occurred spontaneously with various transaction modes, WAL modes, and client interfaces; there was no obvious cause. Nodes would run for a few hundred to a few thousand seconds before exiting. No error messages were printed. These crashes ( #81 ) no longer appeared in 1.1.18.11.rc-18. 3.1.3 Deadlock After Two Transactions (#27) In ParticleDB 1.1.18.8, submitting as few as two concurrent transactions to a healthy, single-node deployment could cause it to deadlock. This occurred both using the Postgres and ParticleDB interfaces. The node would log an error message like [DEADLOCK] 1 cycles detected at SystemTime ... , and an empty backtrace. In some cases new clients could attach and perform transactions; in others, new clients would also hang indefinitely. This may reflect multiple deadlock bugs. With the append workload, version 1.1.18.9 generally could not run for more than 45 seconds without locking up. Version 1.1.18.11.rc-1 could reliably run for two minutes without lockups, and we declared the issue ( #27 ) resolved. 3.1.4 Deadlock With table-2pl (#71) While version 1.1.18.11.rc-1 fixed the most frequent deadlocks, we continued to find deadlocks through 1.1.18.11.rc-6 when running with table-2pl . An otherwise healthy ParticleDB node would execute transactions for about 30 seconds, then get stuck forever. The node would log a similar deadlock error message to #27, and all requests with the ParticleDB client would throw PDB JDBC: null after a 100 second default timeout. These deadlocks ( #71 ) appeared resolved by 1.1.18.11.rc-7. 3.2 Broken Features Orkes’ public documentation claimed broad support for Postgres features, and the internal operator guide concurred: The engine speaks PostgreSQL v3 wire protocol natively — anything that speaks pgjdbc / libpq / psycopg2 / pq connects unchanged. BEGIN , COMMIT , ROLLBACK , prepared statements, parameterised queries, and extended-query pipelining all work as expected. These claims were somewhat optimistic. ParticleDB was missing support for a wide array of Postgres features, and others were badly broken. 3.2.1 No Aggregates Within CASE (#20) In ParticleDB 1.1.4 through 1.1.18.4, aggregate expressions like COUNT(*) were not supported within CASE expressions. SELECT CASE WHEN COUNT ( * ) = 2 THEN 'CASE_COUNT_STAR_OK' ELSE 'CASE_COUNT_STAR_BAD' END FROM t; This threw Error: cannot evaluate wildcard expression . ParticleDB gained support for this feature ( #20 ) by version 1.1.18.6. 3.2.2 Unsupported Exponentiation (#28) ParticleDB 1.1.4 through 1.1.18.8 did not support the Postgres exponentiation operator: root =&gt; SELECT 2 ^ 3 ; ERROR: unsupported binary operator : PGExp Version 1.1.18.9 added support for the ^ operator ( #28 ). 3.2.3 Malformed Responses for Prepared Statements (#2) In ParticleDB 1.1.4 through 1.1.18.9, any attempt to execute a prepared statement using the Postgres JDBC driver caused an exception like Execution error (NoSuchElementException) at java.util.ArrayDeque/removeFirst . Since the JDBC driver automatically switches to prepared statements after the first few calls to execute() , this rendered the database essentially unusable. As a workaround, we disabled the client’s use of prepared statements. Prepared statements are executed using Postgres’ extended query protocol , which takes place in several (potentially reusable) phases: Parse, Bind, Execute, and so on. Orkes believes that ParticleDB likely failed to return a response for one of those phases, or returned an extra message, causing the client’s queue to underflow. By version 1.1.18.11.rc-1, this issue ( #2 ) appeared fixed. 3.2.4 Most Postgres Queries Fail (#83) In ParticleDB 1.1.18.11.rc-7 through 1.1.18.11.rc-19, many queries using the Postgres interface threw Bad value for type long: some_column . This rendered the database largely unusable. CREATE TABLE ints (a int ); SELECT * FROM ints; -&gt; Bad value for type long : a Orkes believes this issue ( #83 ) was fixed in 1.1.19-rc.12. 3.2.5 Tuples Without Fields (#111) In 1.1.18.11.rc-18 and rc-19, queries with the Postgres interface occasionally threw errors like Received resultset tuples, but no field structure for them . 5 For example, take this test of version 1.1.18.11.rc-19, with no faults, a new strict-serializable transaction mode, and WAL mode sync . It executed a transaction like: BEGIN ; SELECT * FROM t_38; INSERT INTO u_38 (d, a, c, b) VALUES ( null , null , false , &quot;oudt1THxi&quot; ); INSERT INTO t_38 (d, b) VALUES ( false , &quot;BCczDbueXLz9zXnpgbdCeFbC5y6XSEys3&quot; ); COMMIT ; This complained of resultset tuples with no field structure, suggesting an error in ParticleDB’s Postgres protocol state machine. While Jepsen has not tested this version, Orkes reports this issue ( #111 ) was fixed in version 1.1.19-rc.13. 3.2.6 Broken Postgres Authentication (#1) The Postgres wire protocol usually authenticates clients using a username and password. ParticleDB had a --pg-password option, but 1.1.4 through 1.1.18.8 lacked any option to set the username. Some of the documentation indicated the default username was admin , while other pages said it was particledb . Neither appeared to work; the only option was to use --no-auth to disable authentication altogether. Version 1.1.18.11.rc-1 introduced a --pg-username option ( #1 ). 3.2.7 Java Client Could Not Execute Transactions (#3) Version 1.0.0 of the official ParticleDB Java client refused every attempt to execute a transaction. Any call to begin a JDBC transaction, or to execute a BEGIN statement, would result in an error message: PDB wire error 1064: SQL plan error: transaction/session statements do not produce a query plan . ParticleDB 1.1.4 could execute transactions via its Postgres interface, but using the official Java SDK was essentially impossible. This issue ( #3 ) seems to have been resolved by ParticleDB 1.1.15. 3.3 Predicates ParticleDB struggled to interpret predicates. WHERE clauses failed to match rows they should have, or matched unexpected or nonexistent rows.
