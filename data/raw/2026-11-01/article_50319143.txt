What changed . # Overview Linux&#x27;s stable kernels shipped a fix on October 11 and 15, 2026 for CVE-2026-98432 , a use-after-free in the IPv4 TCP handshake that a remote, unauthenticated peer can reach. The kernel&#x27;s own CVE Numbering Authority (CNA) scores it CVSS 3.1 9.8, Critical . The fixed releases are 5.10.272, 5.15.223, 6.1.190, 6.6.159, 6.12.113, 6.18.56, 7.2.10 , and 7.3 , and the bug goes back to Linux 4.4. The upstream fix is a four-line change, but most servers run a distribution&#x27;s kernel, and as of 5:15 PM CDT, October 31, Ubuntu&#x27;s tracker still reads &quot;Vulnerable&quot; for its kernel on every release, and Red Hat, which now rates the bug Critical too, lists RHEL 8, 9, and 10 as affected with no fix. Can&#x27;t patch yet Drop TCP packets that carry IPv4 options ( Atlas&#x27;s interim rule ), turn off multipath TCP if you don&#x27;t use it, and patch hosts with multipath TCP listeners first. Why it&#x27;s urgent: the bug sits in code every Linux server runs when it accepts an IPv4 TCP connection, before any application sees the connection. Anthropic, whose researcher reported it, says its Claude model wrote a working proof-of-concept exploit that runs commands as root on &quot;Linux servers with a multipath TCP listener,&quot; with no credentials. Go programs open those listeners by default, per the Go Security Team. On Amazon Linux 2, the core kernel (ALAS2-2026-4065) and the 5.4, 5.10, and 5.15 Extras kernels (ALAS2KERNEL-5.4-2026-135, ALAS2KERNEL-5.10-2026-137, and ALAS2KERNEL-5.15-2026-120), all October 30 ( CVE page ). # How the vulnerability works When a Linux server accepts a TCP connection, the kernel tracks the half-open handshake in a lightweight &quot;request socket,&quot; then creates a full socket once the handshake completes. If the connecting peer&#x27;s IPv4 header carried options, the kernel keeps them to echo in its replies. The bug: the kernel handed those saved options from the request socket to the new connection without copying them, then freed them immediately when the connection went away, while another CPU could still be reading them to build a handshake reply. Reading freed kernel memory is a use-after-free. The peer needs no login, and it all happens inside the kernel&#x27;s handshake handling, before any application code runs. The CNA&#x27;s scoring notes say the stale data can leak kernel heap memory back to the peer, steer kernel writes out of bounds, or crash the machine. Anthropic says a lost race &quot;only fails the handshake without crashing the whole system, so a determined attacker can retry indefinitely until they succeed.&quot; # The fix Eric Dumazet&#x27;s commit, &quot;ipv4: free inet_opt and ireq_opt after an RCU grace period,&quot; changes two plain kfree() calls to kfree_rcu() , which waits until every reader has finished with the memory before freeing it. Other code paths that replace these options already did that. The commit also fixes the same problem in request-socket migration ( net.ipv4.tcp_migrate_req=1 , or a BPF_SK_REUSEPORT_SELECT_OR_MIGRATE program), and says a related IPv6 case &quot;will be addressed in a separate patch.&quot; ipv4: free inet_opt and ireq_opt after an RCU grace period torvalds/linux · e3f33b0 · Oct 1, 2026 net/ipv4/af_inet.c + 1 − 1 1 lines added, 1 removed net/ipv4/tcp_ipv4.c + 1 − 1 1 lines added, 1 removed 2 files changed + 2 − 2 2 lines added, 2 removed # Which servers are exposed Every Linux host that accepts IPv4 TCP connections on an affected kernel: web servers, SSH, databases, load balancers, and Kubernetes nodes. The CNA&#x27;s notes say the vulnerable path runs &quot;during the TCP handshake, before application authentication.&quot; Hosts with a multipath TCP (MPTCP) listener first. That&#x27;s the setup Anthropic&#x27;s working exploit needs: &quot;Linux servers with a multipath TCP listener.&quot; Anthropic hasn&#x27;t said why that listener matters, and the CVE record doesn&#x27;t mention MPTCP. A server has one only if an application opens an MPTCP socket, and Go programs do by default: the Go Security Team says &quot;as of Go 1.24, Go programs enable MPTCP by default for listen sockets on Linux.&quot; The default follows the go line in the program&#x27;s go.mod , and applies only where the kernel allows MPTCP ( net.mptcp.enabled = 1 , as on the Debian 12 kernel we checked; AlmaLinux says it ships MPTCP off). The Go team adds that &quot;the underlying bug is not specific to MPTCP. It is possible that systems with no MPTCP listeners are vulnerable to similar attacks.&quot; The check is below . Red Hat now rates it as the CNA does. It raised the bug from Important (8.1) to Critical (9.8) on October 30, citing &quot;the lack of network prerequisites and the potential for severe system instability.&quot; Its bulletin says &quot;Systems accepting inbound TCP connections are most directly exposed.&quot; # How to check your systems # Check the kernel Shell Copy 1 uname - r # the running kernel 2 uname - v # Debian: the package version running 3 dpkg - l &#x27;linux-image*&#x27; | grep ^ ii # Debian/Ubuntu: installed kernel packages 4 rpm - q kernel # RHEL and derivatives: installed kernels 5 needs-restarting - r # RHEL (dnf-utils): is a reboot needed? Compare the result with your distribution&#x27;s status above , not with the upstream version. If the installed kernel is newer than the running one, the fix isn&#x27;t active until you reboot. Run these on container hosts and Kubernetes nodes, not inside containers: a container reports the host&#x27;s kernel. We ran them on a Debian 12 host and in a Rocky Linux 9 container. # Check for multipath TCP listeners Shell Copy 1 ss - Mlnp # MPTCP listening sockets and the processes that own them 2 sysctl net . mptcp . enabled # 1 means applications may open MPTCP sockets ss -M lists only MPTCP sockets, so an empty result means no MPTCP listener. net.mptcp.enabled = 1 alone doesn&#x27;t create one: an application has to open an MPTCP socket. We tested both with iproute2 6.1 in a Debian 12 container, where ss -Mlnp listed a test MPTCP listener and skipped a plain TCP one beside it. On October 31 it also listed a Go HTTP server whose go.mod says go 1.24 , and skipped the same server built with go 1.23 . # How to fix # Update the kernel and reboot Install your distribution&#x27;s fixed kernel as soon as it ships, then reboot: a kernel update doesn&#x27;t take effect until the machine boots into it. Reboot container hosts and Kubernetes nodes too. Appliances and cloud images that bundle a kernel need their vendor&#x27;s update. On Debian, SUSE Linux Enterprise Server 16.0 and the 15 LTSS releases, openSUSE Leap 16.0, Oracle Linux&#x27;s UEK kernels, and Amazon Linux 2 and 2023, the fix is out. AlmaLinux&#x27;s is in its testing repository. On Ubuntu and RHEL, it isn&#x27;t out yet, as of 5:15 PM CDT, October 31. Watch the trackers linked above . Running a self-built kernel? Move to the fixed stable release for its line. # If you can&#x27;t patch yet Red Hat&#x27;s bulletin and AlmaLinux now publish nftables rules that drop incoming IPv4 TCP packets carrying IP options. Red Hat says its rule &quot;reduces exposure to this vulnerability but cannot fully prevent it.&quot; The following is Atlas&#x27;s interim recommendation, the same rule as AlmaLinux&#x27;s, based on the CNA&#x27;s scoring notes, which say the attacking peer supplies IPv4 Record Route or Timestamp options in its SYN. TCP traffic almost never carries IPv4 options legitimately, so dropping TCP packets that have them should cost nothing: Shell Copy 1 nft add table ip cve_2026_98432 2 nft add chain ip cve_2026_98432 pre &#x27;{ type filter hook prerouting priority -300; }&#x27; 3 nft add rule ip cve_2026_98432 pre meta l4proto tcp ip hdrlength gt 5 counter drop ip hdrlength gt 5 matches any IPv4 header longer than the 20-byte minimum, which only options produce. The rule runs before connection tracking and doesn&#x27;t touch IPv6 or non-TCP traffic. We tested it in a Debian 12 container: it dropped a SYN carrying a Record Route option, and ordinary TCP connections still worked. We haven&#x27;t tested it against an exploit, and it doesn&#x27;t fix the kernel. It lasts until reboot, which is fine if the reboot is into a fixed kernel; remove it with nft delete table ip cve_2026_98432 . If your edge firewall can drop IPv4 packets with options, doing it there protects every host behind it. If you manage the firewall with iptables, this rule does the same job from the raw table, which also runs before connection tracking: Shell Copy 1 iptables - t raw - I PREROUTING - p tcp - m u32 - - u32 &quot;0&gt;&gt;24&amp;0xF=6:15&quot; - j DROP The u32 match reads the IPv4 header-length field, and a value of 6 to 15 means the header carries options. We tested it with iptables 1.8.9, on both its nf_tables and legacy backends, in a Debian 12 container: it dropped a Record Route SYN sent to the host and one routed through it, and ordinary TCP connections still worked. Remove it by running the same command with -D in place of -I ; like the nft rule, it lasts until reboot. It needs the kernel&#x27;s xt_u32 module, which the Debian 12, Ubuntu 22.04 and 24.04, and RHEL 8 kernels include. RHEL 9 and 10 kernels, and their rebuilds, leave it out, so use the nft rule there. Red Hat&#x27;s rule hooks input ; ours hooks prerouting , so it also drops packets the host routes on to containers. On October 31 we tested it against two pairs of network namespaces. It dropped a Record Route SYN routed between one pair, and never saw one bridged between the other, as AlmaLinux warns: &quot;Traffic between containers on the same host may bypass it.&quot; AlmaLinux also says not to use it on networks that rely on CIPSO security labels, which travel in IPv4 options. Turn off multipath TCP if you don&#x27;t use it. That removes the setup Anthropic&#x27;s exploit needs, though not the bug. AlmaLinux&#x27;s steps: Shell Copy 1 echo &#x27;net.mptcp.enabled = 0&#x27; | sudo tee / etc / sysctl . d / 9 0 - disable-mptcp . conf 2 sudo sysctl - w net . mptcp . enabled = 0 3 sudo ss - Mlnp # listeners opened earlier stay MPTCP: restart their services New MPTCP sockets then fail, and Go programs fall back to plain TCP when they start. The setting is per network namespace, and each new one starts with MPTCP on, so a container keeps it unless you set it there too (Docker: --sysctl net.mptcp.enabled=0 ). We tested the steps and the Docker flag on October 31. For a single Go program, GODEBUG=multipathtcp=0 in its environment turns the default off, but the Go Security Team calls disabling MPTCP program by program &quot;a fragile mitigation.&quot; Until you can patch, keep MPTCP listeners off the internet, and put the hosts that have one at the top of the patch list. # Timeline and exploitation status All times are CDT (UTC−5).
