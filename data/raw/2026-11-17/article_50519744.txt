Introduction In programming, a datetime library&rsquo;s core functionality rests at the intersection of a computer system&rsquo;s concept of time and a human&rsquo;s concept of time. The prevailing notion of system time is Unix time . A human&rsquo;s concept of time is far more complex, but the most popular such model is the Gregorian calendar coupled with either a 12-hour or 24-hour clock. At the core of every datetime library rests some routine for converting between these concepts. A datetime library typically provides much more than this. Indeed, datetime handling has historically been very difficult . My own belief is that the difficulty comes from poor modeling of the domain . Instead of encapsulating the complexity inside a reusable bundle of code, many datetime libraries pass some or all of the complexity on to its users. Jiff instead tries hard to encapsulate the complexity and make it difficult for users to do something wrong. ( Jiff is not the first to do this! ) In this section of the blog, we&rsquo;ll do some very basic introductions. Follow Along To follow along with the examples in this blog, create a new Cargo project with dependencies on jiff and anyhow : mkdir jiff-playground cd jiff-playground cargo init --bin cargo add jiff anyhow $EDITOR src/main.rs Most examples are a complete self-contained Rust program. Just copy the code and replace whatever is in src/main.rs . Then run the program: cargo run Terms I am loath to present a dictionary. However, the datetime domain is littered with confusable terms, so I think it&rsquo;s important to orient ourselves on a shared vocabulary. I&rsquo;ve kept this section as small as possible. (Some terms, like &ldquo;time zone,&rdquo; are omitted here because they are best defined through exploration in the sections that follow.) Civil time : The time you see on your clock. And in general, the time that the humans in your approximate geographic vicinity also see. That is, civil time is a human coordinated agreement for communicating time in a particular geographic region. Civil time is also known as: local time, plain time, naive time, clock time and others. UTC : An abbreviation for Coordinated Universal Time ; it is a time standard that serves as the basis for civil time around the world. It was originally intended to roughly correspond to mean solar time . TAI : An abbreviation for International Atomic Time ; it is a time standard as measured by atomic clocks. It isn&rsquo;t directly connected to mean solar time. Leap second : An adjustment to TAI to bring it closer to mean solar time and thus forming the basis of UTC. Unix time : UTC, but ignoring leap seconds. TAI and leap seconds won&rsquo;t be a feature of this blog, but they are listed here in order to convey the difference between Unix time and UTC. The DateTime Onion As a way to transition into some of the core types of Jiff, I&rsquo;ve come to think of its datetime types like an onion. In reverse order, we can build up its layers all the way to a ZonedDateTime . So let&rsquo;s start with more terms, but this time, they are also types in Jiff: A civil::Date is a plain Gregorian date, unattached to any specific location. A civil::Time is a plain time on a clock, to nanosecond precision, unattached to any specific location. A civil::DateTime combines a civil::Date and a civil::Time to provide both a Gregorian date and a time on a clock. It is also unattached to any specific location. A Timestamp is an unambiguous specific instant in time regardless of geographic location, represented as the number of nanoseconds since the Unix epoch. A TimeZone is a set of rules for mapping a Timestamp to a civil::DateTime , and vice versa, in a specific geographic region. A ZonedDateTime combines a Timestamp , a civil::DateTime and a TimeZone to represent a specific instant in time in a specific geographic location. To make this a bit more concrete, we can see what this looks like in code. Since a time zone can map from a civil datetime to an instant in time, one way to create a zoned datetime requires only a civil datetime and a time zone: use jiff :: civil ; fn main () -&gt; anyhow :: Result &lt; () &gt; { let date = civil :: date ( 2026 , 11 , 1 ); let time = civil :: time ( 17 , 30 , 0 , 0 ); let datetime = date . to_datetime ( time ); // zdt is an initialism for &#34;ZonedDateTime&#34; let zdt = datetime . in_tz ( &#34;America/New_York&#34; ) ? ; assert_eq! ( zdt . timestamp (). as_second (), 1793572200 ); Ok (()) } Another way to create a zoned datetime requires only a timestamp and a time zone. This is because time zones can also map a timestamp to a particular civil datetime: use jiff :: { civil , Timestamp }; fn main () -&gt; anyhow :: Result &lt; () &gt; { let timestamp = Timestamp :: from_second ( 1793572200 ) ? ; let zdt = timestamp . in_tz ( &#34;America/New_York&#34; ) ? ; // This is a shortcut for creating a civil datetime. // The previous example spells it out a bit more verbosely // for clarity. let expected = civil :: date ( 2026 , 11 , 1 ). at ( 17 , 30 , 0 , 0 ); assert_eq! ( zdt . datetime (), expected ); Ok (()) } Notice how we get the equivalent zoned datetime in both cases, but we come at it from different directions. In the first case, we start with a time that we might see on our clocks and calendars. In the second case, we start with a particular instant in time that we might get from a database or file system or some other system call. Defining a time zone There is one piece missing from the zoned datetime onion examples: the time zone offset . An offset represents the amount of time one must adjust UTC time in order to get civil time. For example, consider the time 2026-11-01T22:30:00 in UTC. In order to get the civil datetime for someone living in New York, one would subtract 5 hours: 2026-11-01T22:30:00 - 05:00 = 2026-11-01T17:30:00 Indeed, every zoned datetime has an offset associated with it: use jiff :: { civil , tz , Timestamp }; fn main () -&gt; anyhow :: Result &lt; () &gt; { let timestamp = Timestamp :: from_second ( 1793572200 ) ? ; let zdt = timestamp . in_tz ( &#34;America/New_York&#34; ) ? ; assert_eq! ( zdt . offset (). seconds (), - ( 5 * 60 * 60 )); let dt = civil :: date ( 2026 , 11 , 1 ). at ( 17 , 30 , 0 , 0 ); let zdt = dt . in_tz ( &#34;America/New_York&#34; ) ? ; assert_eq! ( zdt . offset (), tz :: offset ( - 5 )); Ok (()) } NOTE : The America/New_York string you see in the above example is an IANA Time Zone Database Identifier. The IANA Time Zone Database is a collection of time zone definitions that can be referenced by a short identifier string. Examples: Australia/Sydney , Asia/Tokyo , Europe/Berlin . When a civil datetime is combined with an offset, then what you get is always an instant in time. With the concept of an offset introduced, we can now give a more precise definition of a time zone. A time zone is a geographic region in which civil clocks agree and which provides the following: A mapping from an instant in time to an offset from UTC. The offset applied to an instant yields a civil datetime. A mapping from a civil datetime to a possibly ambiguous offset from UTC. The offset applied to a civil datetime yields an instant. Both mappings have been demonstrated in prior examples, but the mapping from civil datetime to an offset seems to be rather complicated due to some potential ambiguity. When does that ambiguity arise? An ambiguous offset occurs when the civil datetime either doesn&rsquo;t correspond to a valid clock time in this time zone (e.g., when clocks are moved ahead for daylight saving time ) or where there could be multiple valid clock times (e.g., when clocks are moved backward for daylight saving time ). Let&rsquo;s look at some examples. In this first example, we&rsquo;ll take a look at times around the daylight saving time transition from summer time to standard time in New York. In New York, the clocks were &ldquo;set back&rdquo; by an hour at exactly 2AM. This caused the 1AM hour to repeat itself. use jiff :: { civil :: date , tz :: { offset , TimeZone }, }; fn main () -&gt; anyhow :: Result &lt; () &gt; { let tz = TimeZone :: get ( &#34;America/New_York&#34; ) ? ; // During summer time, New York&#39;s offset from UTC is -04:00. let zdt = date ( 2026 , 11 , 1 ). at ( 0 , 30 , 0 , 0 ). to_zoned_datetime ( tz . clone ()) ? ; assert_eq! ( zdt . offset (), offset ( - 4 )); // During standard time, New York&#39;s offset from UTC is -05:00. let zdt = date ( 2026 , 11 , 1 ). at ( 2 , 30 , 0 , 0 ). to_zoned_datetime ( tz . clone ()) ? ; assert_eq! ( zdt . offset (), offset ( - 5 )); // But what does 01:30AM mean? Is it the first repetition or the second? // Jiff automatically chooses the first by default. let zdt = date ( 2026 , 11 , 1 ). at ( 1 , 30 , 0 , 0 ). to_zoned_datetime ( tz . clone ()) ? ; assert_eq! ( zdt . offset (), offset ( - 4 )); Ok (()) } The above example shows how Jiff resolves the ambiguity when a &ldquo;fold&rdquo; occurs, or when there is a time zone transition that moves the civil time backwards. But we can actually dig down into lower level APIs to change how that ambiguity is resolved. By default, Jiff uses a &ldquo;compatible&rdquo; strategy that always selects the first repetition of a time in a fold. But other strategies can be selected by using APIs on a TimeZone directly: use jiff :: { civil :: date , tz :: { offset , TimeZone }, }; fn main () -&gt; anyhow :: Result &lt; () &gt; { let tz = TimeZone :: get ( &#34;America/New_York&#34; ) ? ; let dt = date ( 2026 , 11 , 1 ). at ( 1 , 30 , 0 , 0 ); // The same that Jiff uses by default. let zdt = tz . to_ambiguous_zoned_datetime ( dt ). compatible () ? ; assert_eq! ( zdt . offset (), offset ( - 4 )); // Always selects the earlier datetime. // For a fold, this is the same as the // default &#34;compatible&#34; strategy. let zdt = tz . to_ambiguous_zoned_datetime ( dt ). earlier () ? ; assert_eq! ( zdt . offset (), offset ( - 4 )); // Always selects the later datetime. // For a fold, this selects the second // occurrence of the 1AM hour! let zdt = tz . to_ambiguous_zoned_datetime ( dt ). later () ? ; assert_eq! ( zdt . offset (), offset ( - 5 )); // Always returns an error when there // is any ambiguity. assert_eq! ( tz . to_ambiguous_zoned_datetime ( dt ) . unambiguous () . unwrap_err () . to_string (), &#34;error converting datetime to instant in time zone America/New_York: \ datetime is ambiguous \ since it falls into a fold between offsets -04 and -05&#34; , ); Ok (()) } The same idea applies to gaps , or time zone transitions where there&rsquo;s some civil time that gets skipped on civil clocks. For example, on March 8, 2026 at 2AM, civil time skipped ahead to 3AM: use jiff :: { civil :: date , tz :: { offset , TimeZone }, }; fn main () -&gt; anyhow :: Result &lt; () &gt; { let tz = TimeZone :: get ( &#34;America/New_York&#34; ) ? ; let dt = date ( 2026 , 3 , 8 ). at ( 2 , 30 , 0 , 0 ); // The &#34;compatible&#34; strategy selects // the later time in the case of gaps. let zdt = tz . to_ambiguous_zoned_datetime ( dt ). compatible () ? ; assert_eq! ( zdt . offset (), offset ( - 4 )); // Always selects the earlier datetime. // For a gap, this selects the hour // before the gap. let zdt = tz . to_ambiguous_zoned_datetime ( dt ). earlier () ? ; assert_eq! ( zdt . offset (), offset ( - 5 )); // Always selects the later datetime. // For a gap, this is the same as the // default &#34;compatible&#34; strategy. let zdt = tz . to_ambiguous_zoned_datetime ( dt ). later () ? ; assert_eq! ( zdt . offset (), offset ( - 4 )); // Always returns an error when there // is any ambiguity. assert_eq! ( tz . to_ambiguous_zoned_datetime ( dt ) . unambiguous () . unwrap_err () . to_string (), &#34;error converting datetime to instant in time zone America/New_York: \ datetime is ambiguous \ since it falls into a gap between offsets -05 and -04&#34; , ); Ok (()) } Durations There are two remaining core types, both representing some notion of a duration: Span is a powerful hybrid duration that combines both calendar units (years, months, weeks, days) and physical time units (hours, minutes, seconds, milliseconds, microseconds, nanoseconds). It is a beefy type that preserves the individual unit values. SignedDuration is a signed version of std::time::Duration and always corresponds to a 96-bit integer number of nanoseconds. It can only represent physical time (units of hours or smaller) and not calendar units (units of days or greater). A Span is the preferred duration type to use whenever possible. Here&rsquo;s a simple example that shows how to get the number of days between two civil dates: use jiff :: civil :: date ; fn main () -&gt; anyhow :: Result &lt; () &gt; { let d1 = date ( 2024 , 2 , 1 ); let d2 = date ( 2024 , 3 , 1 ); let span = d2 - d1 ; assert_eq! ( span . get_days (), 29 ); // or, equivalently: assert_eq! ( d1 . until ( d2 ) ? . get_days (), 29 ); // Flipping d1 and d2 gives the same result, // but negative. let span = d1 - d2 ; assert_eq! ( span . get_days (), - 29 ); Ok (()) } Durations can also be added to dates: use jiff :: { civil :: date , ToSpan }; fn main () -&gt; anyhow :: Result &lt; () &gt; { let d1 = date ( 2024 , 2 , 1 ); // This convenient syntax comes from the // `ToSpan` extension trait. let span = 29. days (); assert_eq! ( d1 . checked_add ( span ) ? , date ( 2024 , 3 , 1 )); Ok (()) } Generally speaking, whenever there is an operation involving a Span , there is an equivalent operation available with SignedDuration : use jiff :: { civil :: date , SignedDuration }; fn main () -&gt; anyhow :: Result &lt; () &gt; { let dt1 = date ( 2024 , 2 , 1 ). at ( 17 , 30 , 0 , 0 ); let sdur = SignedDuration :: from_mins ( 90 ); assert_eq! ( dt1 . checked_add ( sdur ) ? , date ( 2024 , 2 , 1 ). at ( 19 , 0 , 0 , 0 )); Ok (()) } Notice that in the above example, we actually switched from using a civil::Date to a civil::DateTime . This was done to show how physical time units can be added. But note that the same can be accomplished with a Span , because it combines all units: use jiff :: { civil :: date , ToSpan }; fn main () -&gt; anyhow :: Result &lt; () &gt; { let dt1 = date ( 2024 , 2 , 1 ). at ( 17 , 30 , 0 , 0 ); let span = 1. hour (). minutes ( 30 ); assert_eq! ( dt1 . checked_add ( span ) ? , date ( 2024 , 2 , 1 ). at ( 19 , 0 , 0 , 0 )); // Calendar and physical time units can // be combined! let span = 1. month (). hours ( 1 ). minutes ( 30 ); assert_eq! ( dt1 . checked_add ( span ) ? , date ( 2024 , 3 , 1 ). at ( 19 , 0 , 0 , 0 )); Ok (()) } In brief, use a Span when you can. But when it&rsquo;s too bulky or too slow, use a SignedDuration . One of the key benefits of a Span is that since it represents each unit value distinctly, one can preserve the original meaning of a duration. For example, it&rsquo;s common to represent the runtime of films in minutes, even when the duration exceeds one hour. Indeed, a span of 2 hours is a distinct span from a span of 120 minutes: use jiff :: ToSpan ; fn main () -&gt; anyhow :: Result &lt; () &gt; { let span1 = 2. hours (); let span2 = 120. minutes (); // This means the spans are distinct values // in memory. assert_ne! ( span1 . fieldwise (), span2 . fieldwise ()); Ok (()) } The Span::fieldwise routine converts a Span into a value whose units can be compared in a field-by-field fashion. To compare spans based on the actual physical duration they represent, use Span::compare : let span1 = 2. hours (); let span2 = 120. minutes (); assert! ( span1 . compare ( span2 ) ? . is_eq ()); This was a very brief introduction to durations in Jiff. They are a lot more powerful than what is shown here. You might even try playing with the examples above to explore its nooks and crannies. We&rsquo;ll cover their API in more detail in a later section. When should I use Jiff? Jiff isn&rsquo;t always the right thing to use. Sometimes you can get by with something simpler. First and foremost, if you&rsquo;re measuring the time something takes in a program, you should almost certainly be using monotonic time. This is available via std::time::Instant : use std :: time :: { Duration , Instant }; fn main () -&gt; anyhow :: Result &lt; () &gt; { let start = Instant :: now (); // do some serious work std :: thread :: sleep ( Duration :: from_secs ( 1 )); let elapsed = Instant :: now (). duration_since ( start ); println! ( &#34; {elapsed:?} &#34; ); Ok (()) } If you do need to compute elapsed time using your system clock, then Jiff is very convenient for that: use std :: time :: Duration ; use jiff :: Timestamp ; fn main () -&gt; anyhow :: Result &lt; () &gt; { // assume `start` came from somewhere // over a network let start = Timestamp :: now (); std :: thread :: sleep ( Duration :: from_secs ( 1 )); let elapsed = Timestamp :: now (). duration_since ( start ); println! ( &#34; {elapsed} &#34; ); Ok (()) } But you don&rsquo;t actually need Jiff for this. A std::time::SystemTime will work perfectly fine: use std :: time :: { Duration , SystemTime }; fn main () -&gt; anyhow :: Result &lt; () &gt; { // assume `start` came from somewhere // over a network let start = SystemTime :: now (); std :: thread :: sleep ( Duration :: from_secs ( 1 )); let elapsed = SystemTime :: now (). duration_since ( start ) ? ; println! ( &#34; {elapsed:?} &#34; ); Ok (()) } Where Jiff starts to become useful is when you need something beyond just an integer number of seconds since the Unix epoch. For example, some very hairy math is required in order to convert a SystemTime into an RFC 3339 timestamp like 2026-11-14T21:34:00Z . As long as you can live in UTC completely, don&rsquo;t care about local time and can work with Unix timestamps only, then the Rust standard library won&rsquo;t steer you wrong.
